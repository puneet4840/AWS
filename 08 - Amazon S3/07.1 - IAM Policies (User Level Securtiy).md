# IAM Policies (User Level Security)

Ab hum S3 Security ke ek bahut important part par aate hain: **IAM Policies**, jise tum is context mein broadly user-level security bhi samajh sakte ho.

Is concept ko samajhna bahut important hai, kyunki S3 bucket secure karne ka matlab sirf bucket ko private bana dena nahi hota. Humein ye bhi decide karna hota hai ki kaunsa IAM user, IAM role, ya application S3 mein exactly kya kar sakta hai.

For example:
- Kaunsa user bucket dekh sakta hai?
- Kaunsa user files upload kar sakta hai?
- Kaunsa user files download kar sakta hai?
- Kaunsa user files delete kar sakta hai?
- Kaunsa user bucket create ya delete kar sakta hai?
- Kya user poori bucket access kar sakta hai ya sirf ek specific folder/prefix?
- Kya EC2 instance S3 access kar sakta hai?
- Kya developer sirf logs upload kar sakta hai lekin unhe delete nahi kar sakta?

In sab permissions ko control karne ke liye **IAM policies** use hoti hain.

<br>

IAM Policies (User Level Security) ka matlab hota hai ki hum User, Group ya Role ko AWS ke IAM service mein jake access provide karte hai. Isme hum S3 ki permissions dete hain, jisse User, Groups ya Role AWS console mein S3 service ko access kar sakta hai.

<br>
<br>

### Sabse pehle IAM Policy kya hoti hai (S3 ke context mein)?

IAM Policy ek JSON document hoti hai jisme hum AWS ko batate hain ki:
- Kaun sa principal(User, Group, Role), AWS ke S3 resource par, kaunsa action perform kar sakta hai, aur kis condition ke under perform kar sakta hai.

IAM policy ka matlab hai ki konsa User, Group ya Role, S3 bucket par konsa action perform kar sakta hai.

<br>

Is definition ko thoda todkar samajhte hain

Ek permission request mein generally kuch important cheezein hoti hain:

**Principal**:

Kaun request kar raha hai?

Example:
- IAM User.
- IAM Role.
- AWS service.
- Federated user.

**Action**:

Wo kya karna chahta hai?

Example:
- s3:GetObject
- s3:PutObject
- s3:DeleteObject
- s3:ListBucket

**Resource**

Wo kis resource par action perform karna chahta hai? Ya konse S3 bucket par action perform karna chta hai?

Example:
```
arn:aws:s3:::my-bucket
```
ya:
```
arn:aws:s3:::my-bucket/*
```

**Effect**:

Permission allow karni hai ya deny?
```
"Effect": "Allow"
```
ya:
```
"Effect": "Deny"
```

**Condition**

Permission kis special condition ke under allowed ya denied hogi?

Example:
- Sirf specific IP address se access.
- Sirf MFA ke saath delete permission.
- Sirf encrypted connection ke through access.
- Sirf specific AWS Region ya account context mein access.

<br>
<br>

### S3 Security mein IAM Policy kya role play karti hai?

Maan lo AWS Account ke andar tumhare paas ek S3 Bucket hai.
```
company-data-bucket
```

Is bucket ke andar objects hain.
```
company-data-bucket
│
├── employees.csv
├── salary.xlsx
├── application-logs/
│
│   ├── app-1.log
│   └── app-2.log
│
└── public-assets/
    ├── logo.png
    └── banner.jpg
```

Ab company mein multiple IAM Users hain.
```
Puneet
Amit
Rahul
Developer-Team (Group)
```

Ab tum nahi chahoge ki sabhi users bucket ke andar sab kuch access kar saken.

For example:
- ho sakta hai Puneet ko sirf application logs dekhne ki permission chahiye.
- Amit ko objects upload karne ki permission chahiye.
- Rahul ko sirf bucket ke kuch specific objects read karne ki permission chahiye.
- Aur kisi normal developer ko salary.xlsx access nahi milni chahiye.

Isi ko manage karne ke liye **IAM Policy** ka role aata hai.

<br>
<br>

### IAM Policy ka basic kaam kya hai?

IAM Policy AWS ko instructions deti hai.

Policy essentially ye define karti hai: Kaun identity kya action kis resource par perform kar sakti hai.

Isko ek formula ki tarah yaad rakh sakte ho:
```
Principal/Identity

+

Action

+

Resource

=

Permission
```

Example:
```
IAM User: Puneet

Action: s3:GetObject

Resource:
arn:aws:s3:::company-data-bucket/*
```
Iska matlab hai ki Puneet ko ```company-data-bucket``` ke objects read karne ki permission di gayi hai.

<br>
<br>

### User ko S3 access automatically nahi milta

Suppose tum AWS mein ek IAM User create karte ho.
```
User Name: Puneet
```

Sirf IAM User create karne se us user ko automatically S3 bucket access nahi mil jata.

AWS by default evaluate karta hai ki user ke paas requested action ke liye permission hai ya nahi.

Agar appropriate permission nahi hai, to request deny ho jayegi.

For example, agar Puneet AWS Console se bucket open karne ki koshish kare aur uske paas required permissions na hon, to usse access nahi milega.

Isliye hume IAM Policy attach karni padti hai.

<br>
<br>

### IAM Policy kahan attach ki ja sakti hai?

S3 access ke context mein IAM identity-based policies generally attach ki ja sakti hain:
- IAM User ke saath.
- IAM Group ke saath.
- IAM Role ke saath.

**IAM User**:

Human user ke liye.

Example:
```
Puneet
```
Tum Puneet ko permission de sakte ho:
```
s3:GetObject
```

<br>

**IAM Group**

Multiple users ko same permission dene ke liye.

Example:
```
Developers Group

Amit
Rahul
Neha
Puneet
```
Tum group ke saath ek S3 policy attach kar sakte ho. Ab sab members ko same permissions mil sakti hain. Iska benefit ye hai ki har user ke liye individually same policy attach nahi karni padti.

<br>

**IAM Role**:

IAM Role mostly AWS services ya temporary access ke liye bahut important hai. Agar kisi AWS resource ko S3 bucket access karna hai to us resource ko IAM Role ke through access kiya jata hai. IAM Role ko policy attach karte hain, fir resource IAM Role ko assume karta hai, aur resource S3 bucket ki access mil jati hai.

Example:
```
EC2
 │
 ▼
IAM Role
 │
 ▼
S3 Bucket
```

Maan lo tumhari EC2 par application chal rahi hai. Application ko S3 mein files upload karni hain.

Tum AWS access key directly application ke code mein store kar sakte ho, lekin ye insecure approach hai.

Better approach: IAM Role banao, usko S3 ki policy attach karo, EC2 IAM role ko assume karke S3 bucket ko access kar lega.

Isliye production environments mein applications ko S3 access dene ke liye IAM Roles bahut commonly use hote hain.

<br>

### IAM Policy ka basic JSON structure

AWS IAM Policies JSON format mein likhi jaati hain.

Example:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-data-bucket/*"
    }
  ]
}
```
Ab isko ek-ek sentence mein samajhte hain.

**"Version": "2012-10-17"**:

Ye policy language version specify karta hai. Normally IAM policies mein tum yehi value use karoge:
```
2012-10-17
```
Ye policy banne ki date nahi hai. Ye IAM policy language ka version identifier hai.

<br>

**"Statement"**

Statement ke andar actual permission define hoti hai. Ek policy mein ek ya multiple statements ho sakte hain.

Example:
```
"Statement": [
    {
        ...
    },
    {
        ...
    }
]
```

Example:
```
"Statement": [
    {
        "Effect": "Allow",
        "Action": "s3:GetObject",
        "Resource": "..."
    }
]
```

<br>

**Effect kya hota hai?**

Effect batata hai ki policy permission allow kar rahi hai ya explicitly deny kar rahi hai.

Example:
```
"Effect": "Allow"
```
Matlab specified action allow hai.

Aur:
```
"Effect": "Deny"
```
Matlab specified action explicitly deny hai.

AWS IAM ka ek bahut important rule hai:
- Explicit Deny generally Allow ko override karta hai.

Example ke liye maan lo Puneet ke paas ek policy hai jo S3 objects read karne ki permission deti hai.
```
Allow → s3:GetObject
```
Lekin kisi applicable policy mein explicitly likha hai:
```
Deny → s3:GetObject
```
To request deny ho sakti hai, kyunki explicit deny evaluation mein precedence rakhta hai.

<br>

**Action kya hota hai?**

Action batata hai ki user S3 ke saath kya operation perform kar sakta hai.

Example:
```
"Action": "s3:GetObject"
```
Iska matlab user object read ya download kar sakta hai.

Kuch common S3 actions hain:

- ```s3:ListBucket```:

Ye bucket ke objects ki listing se related permission hai.

- ```s3:GetObject```:

Ye object read/download karne ke liye use hoti hai.

- ```s3:PutObject```

Ye object upload ya write karne ke liye use hoti hai.

- ```s3:DeleteObject```

Ye object delete karne ke liye use hoti hai.

- ```s3:*```

Ye wildcard pattern S3 ke all actions ko allow karne ke liye use ho sakta hai, lekin production mein unnecessarily broad permissions dena generally avoid karna chahiye.

<br>

**Resource kya hota hai?**

Resource batata hai ki permission kis AWS resource ke liye apply hogi.

S3 ke case mein resource ARN use hota hai.

Example:
```
arn:aws:s3:::company-data-bucket
```
Ye bucket ARN hai.

Aur:
```
arn:aws:s3:::company-data-bucket/*
```
Ye bucket ke andar objects ko represent karta hai.

<br>

**arn:aws:s3:::company-data-bucket (Bucket-Level ARN)**

Yeh ARN sirf aur sirf S3 Bucket (Container) ko point karta hai, uske andar ki files ko nahi.
- Iska Matlab: "Main sirf ```company-data-bucket``` naam ke dabbe (box) ki baat kar raha hoon."
- Yeh Kab Kaam Aata Hai? Jab aapko aisi permissions deni hon jo poori bucket par lagti hain (na ki andar ki files par).

Examples (Bucket Actions):
- s3:ListBucket (Bucket ke andar kaun-kaun si files hain, unki list dekhna).
- s3:PutBucketPolicy (Bucket par koi security rule lagana).
- s3:DeleteBucket (Poori ki poori bucket ko hi delete kar dena).

<br>

**arn:aws:s3:::company-data-bucket```/*``` (Object-Level ARN)**

Yahan jo ```/*``` (Wildcard) laga hai, iska matlab hai "Is bucket ke andar maujood saare objects/folders/files".
- Yeh Kab Kaam Aata Hai? Jab aapko files ke upar koi action lena ho (read, write, delete).

Examples (Object Actions):
- s3:GetObject (Kisi file/picture ko download ya view karna).
- s3:PutObject (Nayi file upload karna ya purani ko overwrite karna).
- s3:DeleteObject (Kisi specific file ko delete karna).

### IAM Policies Examples

**GetObject permission ka example**:

Policy:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-data-bucket/*"
    }
  ]
}
```

Is policy ka matlab hai:
- Puneet ```company-data-bucket``` ke objects read kar sakta hai.

Lekin is policy se automatically bucket contents list karne ki permission nahi milti. Bucket ke content list karne ke liye tumko alag se policy create karni hoti hai.

<br>

**ListBucket ke liye alag permission kyun?**

Maan lo tum S3 Console mein bucket open karna chahte ho aur uske andar ka data dekhna chahte ho.

AWS ko bucket-level listing permission chahiye hoti hai.

Iske liye action hota hai:
```
s3:ListBucket
```
Aur resource hota hai:
```
arn:aws:s3:::company-data-bucket
```
Dhyan do, yahan ```/*``` nahi hai.

Example:
```
{
  "Effect": "Allow",
  "Action": "s3:ListBucket",
  "Resource": "arn:aws:s3:::company-data-bucket"
}
```

Isliye ek common read-only policy mein hume do permissions deni pad sakti hain.

Bucket ko list karne ke liye
```
s3:ListBucket
```
Aur:

Objects ko read karne ke liye
```
s3:GetObject
```

<br>

**ListObject aur GetObject mein kya difference hai?**

**List Object (Sirf Files Ki List Dekhna)**:

Maan lijiye aapne S3 bucket mein 100 photos upload kar rakhi hain. Jab aap AWS Console kholte hain ya command chalate hain, toh jo aapko saamne 100 photos ke naamon ki list dikhti hai, use List Object kehte hain.
- Isme kya milta hai? Aapko sirf file ka naam, file ka size (jaise 5 MB), aur file kab upload hui thi—yeh choti-moti basic jaankari milti hai.
- Isme kya nahi milta? Isme aapko photo ke andar kya hai, wo dikhai nahi deta.
- AWS Rule: Yeh permission poore dabbe (Bucket) par lagti hai (arn:aws:s3:::my-bucket). Agar aapke paas yeh permission hai, toh aap bucket ke andar jhaank kar dekh sakte hain ki kaun-kaun si files rakhi hain.

**Get Object (Asli File Ko Download Ya View Karna)**:

Jab aap list mein se kisi ek specific photo par click karte hain aur use Download karte hain ya screen par Open karte hain, toh use Get Object kehte hain.
- Isme kya milta hai? Isme aapko file ka asli data milta hai. Agar video hai toh video chalne lagegi, text file hai toh andar ka text padh payenge.
- Isme kya nahi milta? Isse aap baaki files ke naam nahi jaan sakte, yeh sirf usi ek file ke liye kaam karta hai jise aapne maanga hai.
- AWS Rule: Yeh permission bucket ke andar rakhi files par lagti hai (arn:aws:s3:::my-bucket/*).

Agar aapke paas List Object ki permission nahi hai, lekin aapko pata hai ki bucket ke andar puneet-photo.jpg naam ki file rakhi hai, aur aapke paas Get Object ki permission hai... toh aap bina list kiye hi seedhe us photo ko download kar sakte hain!

<br>

**Complete Read-Only Policy**

Ab maan lo Puneet ko poore bucket ka data dekhna aur download karna hai.

Policy:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-data-bucket"
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-data-bucket/*"
    }
  ]
}
```

Pehla statement bol raha hai:
- User bucket ke contents list kar sakta hai.

Doosra statement bol raha hai:
- User bucket ke andar ke objects read kar sakta hai.

<br>

**User ko object upload permission dena**

Ab maan lo Puneet application team mein hai aur usko logs upload karne hain.

Bucket hai: ```company-data-bucket```.

Logs ek specific prefix mein upload honge:
```
application-logs/
```

Hum poore bucket par permission dene ke bajaye sirf isi prefix par permission de sakte hain.

Example:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::company-data-bucket/application-logs/*"
    }
  ]
}
```

Iska matlab hai:
- Puneet sirf ```application-logs/``` prefix ke andar objects upload kar sakta hai.

Wo theoretically is permission ke basis par bucket ke doosre prefixes mein object upload nahi kar sakta.

Example:

Allowed:
```
application-logs/app.log
```
Allowed:
```
application-logs/2026/january/app.log
```
Lekin ye permission automatically allow nahi karegi:
```
salary.xlsx
```
Ya:
```
employees/employee-data.csv
```
Is concept ko **Least Privileg**e bolte hain.


<br>

**Read aur Write dono permissions**

Maan lo application team ko logs upload bhi karne hain aur purane logs read bhi karne hain.

Policy:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::company-data-bucket"
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-data-bucket/application-logs/*"
    }
  ]
}
```

Is policy mein user bucket-level listing kar sakta hai. Aur ```application-logs/``` prefix ke andar objects read aur upload kar sakta hai.

<br>

**Kisi specific folder/prefix par access kaise control karte hain?**

Normal S3 bucket mein actual filesystem folders nahi hote. Isliye IAM Policy mein hum technically object key prefix ke basis par access control karte hain.

Suppose bucket:
```
company-data-bucket
```
Aur objects:
```
dev/app.log
dev/config.json

prod/app.log
prod/config.json
```

Ab Dev team ko sirf ```dev/``` Access chahiye.

Policy:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::company-data-bucket/dev/*"
    }
  ]
}
```

Iska matlab hai:
```
dev/app.log
```
Allowed hai.

Aur:
```
dev/config.json
```
Allowed hai.

Lekin:
```
prod/app.log
```
Is Allow statement ke scope mein nahi aata.

### IAM Policy user-level security ka actual flow

Ab complete request flow samajhte hain.

Suppose Puneet AWS CLI use kar raha hai.

Command:
```
aws s3 cp test.txt s3://company-data-bucket/application-logs/test.txt
```

Ab background mein conceptually kya hota hai?

**Step 1**:

Puneet AWS credentials ke through authenticate karta hai. AWS identify karta hai ki request kis IAM principal se aa rahi hai.

**Step 2**:

AWS dekhta hai ki Puneet kya action perform karna chahta hai.

Is case mein:
```
s3:PutObject
```

**Step 3**

AWS dekhta hai ki target resource kya hai.
```
arn:aws:s3:::company-data-bucket/application-logs/test.txt
```

**Step 4**

AWS applicable policies evaluate karta hai.

For example:
- IAM User Policy.
- IAM Group Policy.
- IAM Role permissions, agar applicable authentication flow ho.
- S3 Bucket Policy.
- Explicit Deny policies.
- Permission Boundary.
- AWS Organizations SCP, agar account organization mein hai.
- Other relevant policy controls.

**Step 5**

Agar required action explicitly allow hai aur koi applicable explicit deny request ko block nahi kar rahi, to request allowed ho sakti hai. Agar valid allow nahi milta, to implicit deny ke principle ke according request deny ho jati hai.

### IAM User Policy aur S3 Bucket Policy mein basic difference

AWS S3 mein IAM Policy aur Bucket Policy dono ka kaam ek hi hai—security lagana aur yeh tay karna ki kaun data access kar sakta hai aur kaun nahi. Lekin dono ke kaam karne ka tareeqa aur jagah bilkul alag hoti hai.

Asaan bhasha mein farq yeh hai ki ek policy **User** par lagti hai aur dusri policy **Bucket** par lagti hai.

**IAM Policy (Identity-Based)**:

Yeh policy aap AWS IAM (Identity and Access Management) ke andar banate hain aur ise kisi specific User, Group, ya Role ke sath attach (baandh) karte hain.
- Yeh kya kehti hai? "Main is specific user (jaise Rahul) ko yeh yeh permissions deta hoon."
- Yeh kaise kaam karti hai? Rahul jab bhi AWS mein login karega, uske sath yeh policy chalegi. Woh jis bhi bucket par jayega, AWS check karega ki Rahul ki apni IAM policy mein use allow kiya gaya hai ya nahi.
- Fayda: Agar aapko ek hi employee ko S3, EC2, aur RDS teeno ki permissions deni hain, toh aap ek hi IAM policy banakar us user par laga sakte hain.

<br>

**Bucket Policy (Resource-Based)**:

Yeh policy aap direct S3 Bucket ke andar (Properties -> Permissions) mein jaakar lagate hain. Yeh ek JSON script hoti hai jo seedhe us dabba (bucket) par chipak jaati hai.
- Yeh kya kehti hai? "Meri is bucket ke andar kaun aa sakta hai aur kaun nahi, yeh main tay karungi."
- Yeh kaise kaam karti hai? Duniya ka koi bhi user (chahe aapki company ka ho ya dusri company ka) jab us bucket ko access karne ki koshish karega, toh bucket ki apni policy use check karegi.
- Fayda: Agar aapko apni bucket ko poori duniya ke liye public karna hai (jaise website host karne ke liye), ya kisi dusre AWS account ke user ko permission deni hai, toh Bucket Policy sabse best hai.

<br>

**Ek Zaroori Baat: Agar Dono Policies Lagi Hon Toh Kya Hoga?**

AWS ka ek basic rule hai: **"Explicit Deny Wins"**.

Agar IAM policy keh rahi hai ki "Rahul file download kar sakta hai", lekin Bucket Policy keh rahi hai ki "Rahul file download NAHI kar sakta", toh AWS Rahul ko Block (Deny) kar dega. Kisi bhi kaam ko karne ke liye dono jagah se permission honi chahiye, ya kam se kam ek jagah se Allow aur dusri jagah par Neutral/Allow hona chahiye.
