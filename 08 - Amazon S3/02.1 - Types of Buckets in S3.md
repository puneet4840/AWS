# Types of Buckets in S3

Pehle S3 mein practically sirf General Purpose Bucket hota tha, lekin ab AWS ne S3 ko alag-alag workload ke hisaab se redesign kiya hai. Aaj ke time par S3 mein 4 major bucket types hain.

4 types of buckets in S3:
- **General Purpose Buckets** (Sabse zyada use hone wala standard type).
- **Directory Buckets** (High-performance aur ultra-low latency ke liye).
- **Table Buckets** (Analytics aur Apache Iceberg workloads ke liye).
- **Vector Buckets** (AI aur Machine Learning embeddings ke liye).

Amazon S3 mein bucket ek top-level storage container/resource hai jiske andar data store kiya jata hai.

<br>

### Genral Purpose Bucket

General Purpose Bucket unstructured data ko objects ke form mein store karne ke liye use kiya hai. Matlab general purpose buckets mein hum kisi bhi type ka data store kar sakte hain, lekin vo data ek object ke form mein store hota hai.

<br>

**Object kya hota hai?**

Amazon S3 mein Object ka matlab hota hai aapki File aur uski saari jaankari (Metadata).

S3 ek Object Storage service hai. Yeh traditional computers ki tarah folders aur sub-folders ke rigid structure mein data save nahi karta, balki har file ko ek independent "Object" bana kar ek flat surface par rakh deta hai.

Jab koi bhi data tum general purpose bucket mein store karte ho to vo ek object hota hai. Us object ke andar mukhya roop se 3 cheezein hoti hain:
- **Data (The File)**: Yeh aapki asli file hoti hai, jaise koi photo (image.jpg), video, document, ya code file.
- **Metadata (Data about Data)**: Yeh file se judi extra jaankari hoti hai. Jaise file ka size kya hai, kab upload hui thi, file ka type (image/jpeg) kya hai, aur ise kisne upload kiya.
- **Key (The Unique Name)**: Yeh object ka unique naam ya path hota hai jisse use pehchana jata hai. Jaise images/2026/my-photo.jpg. S3 mein folders asliyat mein nahi hote, yeh poora naam hi ek "Key" hoti hai.

<br>

Ye S3 ka sabse purana aur sabse widely used bucket type hai.

Agar tum AWS Console mein normally Create Bucket karte ho aur koi special bucket type select nahi karte, to generally ye General Purpose Bucket hota hai.

S3 ka original purpose tha:
- Almost kisi bhi type ka object reliably store karna aur usse internet-scale par access karna.

Jaise:
- Images store karna.
- Videos store karna.
- Documents.
- Backups.
- Logs.
- Static website hosting.
- Application files.

Yaani almost saare traditional S3 workloads isi bucket type par chalte hain.

<br>

**General Purpose Bucket ki sabse important characteristic**:

General Purpose Bucket ke objects multiple Availability Zones mein redundantly stored ho sakte hain, depending on the storage class.

Aur General Purpose Bucket mein tum S3 ki almost poori traditional storage-class family use kar sakte ho, except S3 Express One Zone. AWS specifically batata hai ki S3 Express One Zone Directory Buckets ke liye hai.

For example:
```
General Purpose Bucket
        │
        ├── S3 Standard
        ├── S3 Intelligent-Tiering
        ├── S3 Standard-IA
        ├── S3 One Zone-IA
        ├── Glacier Instant Retrieval
        ├── Glacier Flexible Retrieval
        └── Glacier Deep Archive
```

Lekin:
```
S3 Express One Zone
        ✗
```
General Purpose Bucket ke saath use nahi hoti. Ye storage class directory bucket ke saath use hoti hai.

<br>

**General Purpose Bucket mein "folder" kya hota hai?**

General Purpose Bucket mein traditionally actual filesystem directories nahi hoti.

Suppose object key hai:
```
production/logs/application/app.log
```

AWS Console ise roughly is tarah dikha sakta hai:
```
production/
    logs/
        application/
            app.log
```

Lekin General Purpose Bucket mein ye hierarchy fundamentally **object key prefixes** se represent hoti hai. AWS documentation bhi clearly kehti hai ki general purpose buckets mein actual folder hierarchy nahi hoti; ```/``` prefix ke naming convention ko folder-like structure deta hai.

Isliye:
```
production/logs/app.log
```
ek Object Key hai.

<br>

**General Purpose Bucket ka use kab karoge?**

Maan lo tumhari company ki production web application hai.

Architecture:
```
Internet
    |
    v
ALB
    |
    v
Auto Scaling Group
    |
    +---- EC2
    +---- EC2
    +---- EC2
    |
    v
S3 General Purpose Bucket
```

Application S3 mein store kar sakti hai:
```
user-images/
product-images/
application-artifacts/
reports/
backups/
logs/
```

Ye General Purpose Bucket ke liye perfect workload hai.

<br>
<br>

### Directory Buckets

Directory Bucket S3 ka specialized bucket type hai, jo low-latency/high-performance workloads aur certain data-residency use cases ke liye designed hai.

Matlab Directory bucket ese workload mein use ki jati hai jaya low latency chiaye hoti hai.

Important:
- Directory Bucket ka matlab "General Purpose Bucket ke andar folder" nahi hai.

Ye khud ek bucket type hai.

**Note**: General Purpose Bucket **flat architecture** use karti hai hai objects ko store karne ke liye, lekin Directory bucket **hierarchical structure** mein objects ko organize karti hai.

AWS ne ise introduce kiya taaki extremely low-latency workloads ko optimize kiya ja sake.

Yeh bucket pure region mein spread nahi hota, balki aapko kisi ek specific Availability Zone (AZ) ko chunna padta hai. Yeh data ko true hierarchical file system (folders aur sub-folders) ki tarah manage karta hai. Iski wajah se ismein read/write speed single-digit millisecond (10 guna fast) milti hai.

<br>

**Directory Bucket ka main purpose kya hai?**

Normal General Purpose S3 bucket bahut scalable aur high-performance hai.

Lekin kuch applications ko aur aggressive low latency chahiye.

Example:
```
EC2 / EKS / ECS
      │
      │ Millions of requests
      ▼
     S3
```

Agar application continuously:
```
GET
PUT
GET
GET
PUT
DELETE
GET
```
operations perform kar rahi hai, to storage latency application performance ka major factor ban sakti hai.

Isi type ke workloads ke liye Directory Bucket introduce ki gayi jo **S3 Express One Zone** storage class ka use karti hai.

<br>

**Directory Bucket ka architecture**:

```
AWS Region
     |
     +---- Availability Zone
              |
              v
        Directory Bucket
              |
              +---- directory/
              |       |
              |       +---- object1
              |       +---- object2
              |
              +---- another-directory/
                      |
                      +---- object3
```

Directory Bucket hierarchical directories ko support karta hai.

AWS ke according directory buckets objects ko hierarchical directories mein organize karte hain, aur individual directories horizontally scale kar sakti hain.

<br>

**Directory Bucket mein actual directory concept**:

General Purpose Bucket:
```
images/cat.jpg
```
mein ```images/``` primarily prefix hai.

Directory Bucket mein hierarchical directory model explicitly supported hai.

For example:
```
dataset/
    training/
        image1.jpg
        image2.jpg

    validation/
        image3.jpg
```

<br>

**S3 Express One Zone Kya Hai?**

Ye ek storage class hai jo directory buckets ke saath hi use hoti hai.

Normal S3 storage architecture mein data multi-AZ mein store hota hai. Matlab alag alag availability zones mein store hota hai, high availability ke liye.

Lekin Express One Zone mein data sirf ek single availability zone mein store hota hai.

Ismein sirf aur sirf S3 Express One Zone storage class hi kaam karti hai.

Directory bucket isliye itni fast hoti hai kyuki ye S3 Express One-Zone storage class ka use karti hai, jiska main objective hai ki Compute aur storage ko same Availability Zone mein close rakhkar latency minimize karna. Jab apne servers aur directory bucket same hi availability zone mein honge to data read aur write karne ki speed bohot fast ho jayegi.

Example:
```
AWS Region
│
├── AZ-A
│     │
│     ├── EC2
│     ├── EKS
│     └── S3 Express One Zone
│
├── AZ-B
│
└── AZ-C
```

Agar application AZ-A mein chal rahi hai aur Directory Bucket bhi AZ-A mein hai, to workload ko low-latency access mil sakta hai.

AWS ke according S3 Express One Zone data ko single AZ ke andar multiple devices par redundantly store karta hai, lekin multiple AZs ke across redundancy nahi deta.

<br>

**Directory Bucket ka risk**:

Agar tumhara data:
```
business-critical
```
hai aur tumhare paas uska koi alternate copy nahi hai, to single-AZ architecture ko carefully evaluate karna padega.

AWS documentation explicitly warn karti hai ki AZ outage ki situation mein directory bucket ka data unavailable ho sakta hai aur data-loss risk bhi ho sakta hai.

<br>
<br>

### Table Bucket

AWS ne haal hi mein Amazon S3 Tables feature ke sath is naye bucket type ko introduce kiya hai jo tabular (rows aur columns) data ko manage karne ke liye hai

Table Buckets ko tabular data ke liye design kiya gaya hai.

Tabular data ka matlab hai:
```
Rows + Columns
```

Jaise:
```
customer_id | product | amount | timestamp
------------------------------------------------
101         | Laptop  | 80000  | ...
102         | Phone   | 40000  | ...
103         | Monitor | 20000  | ...
```

Ab tak humne dekha ki normal S3 Bucket mein data "Objects" (raw files) ke roop mein save hota hai. Lekin jab hume laakhon-karodon rows ka data analytical queries ke liye manage karna hota hai, toh raw files ko handle karna mushkil ho jata hai.Isi problem ko solve karne ke liye Apache Iceberg aur AWS ka naya feature S3 Table Bucket kaam mein aate hain. 

<br>

**Table Bucket ko kyu banaya gya?**

Pehle agar aapko S3 mein Excel ya CSV files par SQL queries chalani hoti thi, toh performance slow milti thi. Table buckets direct open-source Apache Iceberg format ko support karte hain. Yeh badi datasets par query karne ki speed ko bohot badha deta hai.

Traditional S3 mein tum raw files store kar sakte ho.

Example:
```
transactions/
    2026-08-01.parquet
    2026-08-02.parquet
    2026-08-03.parquet
```

Lekin modern analytics workloads mein sirf files store karna enough nahi hota. Companies ko tables manage karni hoti hain.

Unhe:
- Query karna hota hai.
- Metadata maintain karna hota hai.
- Table evolution handle karni hoti hai.
- Data maintenance karni hoti hai.
- Analytics engines ke saath integrate karna hota hai.

Isi requirement ke liye AWS ne S3 Tables introduce kiye.

Example:

Maan lo tumhare paas e-commerce transactions hain:
```
Order_ID | Customer | Product | Price | Date
---------|----------|---------|-------|----------
1001     | Amit     | Laptop  | 70000 | ...
1002     | Rahul    | Phone   | 30000 | ...
1003     | Neha     | Tablet  | 40000 | ...
```
Ye tabular data hai.

Traditional S3 mein tum is data ko CSV/Parquet files ke form mein store kar sakte ho.

Lekin large-scale analytics mein problem sirf files store karna nahi hoti.

Problems hoti hain:
- Table metadata management
- File compaction
- Snapshots
- Query performance
- Schema evolution
- Analytics integration
- Storage optimization

Isi problem ko solve karne ke liye AWS ne **S3 Tables** / **Table Buckets** introduce kiye.

<br>

Ye AWS ka relatively naya bucket type hai jo analytics workloads ke liye banaya gaya hai. Matlab aap table bucket mein tabular data ko files mein store karke unme query kar sakte ho. Directly data ko analysis kar sakte ho.

Ye normal object storage jaisa use nahi hota.

Table Buckets specifically **Apache Iceberg** format mein tabular data ko store karta hai.

<br>

**Apache Iceberg Kya Hai?**

Apache Iceberg ek open-source, high-performance table format hai jise bada data (Huge Datasets) manage karne ke liye banaya gaya hai.

Aasan shabdo mein: Apache Iceberg ek software technology hai jo raw files ko ek database table ka roop deti hai.

Ise Netflix ne develop kiya tha kyunki unhe S3 par chalne wale purane formats (jaise Hive) mein bohot performance issues aa rahe the. Iceberg ko aap ek smart management layer ki tarah samajh sakte hain jo Amazon S3 jise object store par rakhi lakho files ko ek single, relational SQL database table ki tarah treat karne ki taqat deti hai.

Pehle jab hum S3 mein hazaron Parquet ya CSV files rakhte the, toh query engine ko pata nahi hota tha ki kaun si file mein kya data hai. Iceberg un saari files ke upar ek Database Table jaisa structure bana deta hai.

Jaise normal S3 mein tabular data (CSv files) stored hain, to jab is files par (Athena ya Spark) jaise tools se analytics matlab query chalate the toh data ko folders ke hisab se partition kiya jata hai (e.g., ```year=2026/month=08/day=29/```).

Problem: Agar aapko kisi specific user ka data chahiye, toh query engine ko pure folder ki hazaron files ko scan karna padta tha, jisse time aur paisa (S3 API costs) dono barbaad hote the.

Solution: Apache Iceberg ne folder-based tracking ko khatam kiya aur File-level tracking shuru ki.

<br>

**Apache Iceberg Kaise Kaam Karta Hai?**

Iceberg pure data ko 3 Layers mein divide karke manage karta hai:
```
[ Catalog Layer ]  --> (S3 Tables / AWS Glue) - Point karta hai latest metadata file ko
       |
[ Metadata Layer ] --> Metadata Files (.json) -> Manifest Lists (.avro) -> Manifest Files (.avro)
       |
[ Data Layer ]     --> Asli data files (.parquet / .orc / .avro)
```

1. Catalog Layer (The Pointer):

Yeh sabse upar ki layer hoti hai jo hamesha yeh track karti hai ki table ka current/latest state kya hai. Jab bhi koi query aati hai, woh pehle Catalog ke paas jaati hai. AWS mein AWS Glue Data Catalog ya Amazon S3 Tables iska kaam karte hain.

2. Metadata Layer (The Brain):

Yeh Iceberg ka sabse important hissa hai. Ismein teen tarah ki files hoti hain:
- Metadata File (.json): Yeh table ka schema (columns), partition specs, aur 'snapshots' ki history store karti hai.
- Manifest List (.avro): Yeh batati hai ki ek specific snapshot mein kaun-kaun si manifest files shamil hain.
- Manifest File (.avro): Yeh actual data files ka track rakhti hai. Ismein har ek data file ke min/max values (statistics) likhe hote hain.

3. Data Layer (The Storage):

Yeh woh jagah hai jahan aapka asli data store hota hai. Iceberg zyada tar Apache Parquet ya ORC columnar formats ka use karta hai jo data ko compress karke kam space mein store karte hain.

AWS ne haal hi mein jo S3 Table Buckets launch kiye hain, unka kaam hi yahi hai ki woh Apache Iceberg format ko backend par khud manage karte hain. Aapko alag se koi setup nahi karna padta, bas table bucket banao aur analytical queries (Athena/EMR se) super-fast speed mein chalao.

<br>

**S3 Par Yeh Kaise Kaam Karta Hai?**

Chaliye dekhte hain ki background mein Amazon S3 aur Apache Athena/Spark ke beech kya hota hai jab aap query chalate hain.

**Purana Tarika (Folder-Based) Kaise Fail Hota Hai?**

Maan lijiye aapke S3 bucket mein ek din ka data hai: ```day=29/```. Is folder ke andar 5,000 Parquet files hain.

Jab aap Athena mein query chalate hain: ```SELECT * FROM orders WHERE day='29' AND user_id='Rahul123';```

- Athena ko catalog (Glue) se yeh toh pata chal jata hai ki ```day=29``` wala folder kahan hai. Woh seedhe us folder par pahunch jata hai.
- Folder ke andar pahunchte hi Athena andha ho jata hai. Use yeh nahi pata ki un 5,000 files mein se Rahul ka data kis file ke andar hidden hai.
- S3 koi proper database nahi hai, woh bas ek file storage hai. Isliye Athena ko majbooran un saari 5,000 files ko ek-ek karke open karna padta hai aur unka content check karna padta hai.
- Agar Rahul ka data sirf 1 file mein tha, tab bhi Athena ne baaki 4,999 files ko faltu mein download aur scan kiya. Isse query slow ho gayi aur aapka AWS bill badh gaya (kyunki AWS S3 mein har file ko touch karne ka paisa lagta hai).

**Apache Iceberg (File-Level) Kaise Game Badalta Hai?**

Iceberg kya karta hai? Woh S3 folders par bilkul bharosa nahi karta. Woh jab bhi S3 mein data save karta hai, toh sath mein ek choti si index file (jise Manifest File kehte hain) bhi bana deta hai.

Is Manifest File ke andar ek simple map (table) hota hai, jo har file ka report card rakhta hai. Kuch aisa dikhta hai:
- ```file_1.parquet``` -> Isme User_ID **A** se leke **K** tak ka data hai.
- ```file_2.parquet``` -> Isme User_ID **L** se leke **S** tak ka data hai.
- ```file_3.parquet``` -> Isme User_ID **T** se leke **Z** tak ka data hai.

Ab Dubara Query Chala Kar Dekhte Hain:

Jab aap dubara query chalate hain (```WHERE user_id='Rahul123'```), toh Athena S3 ke data folder mein ja kar files ko haath bhi nahi lagata.
- Athena sabse pehle us choti si Manifest (index) File ko open karta hai.
- Athena dekhta hai ki ```'Rahul123'``` naam R se shuru hota hai. Aur index file saaf keh rahi hai ki L se S tak ka data sirf ```file_2.parquet``` mein hai!
- Athena baaki saari files ko chhoda deta hai aur seedhe ```file_2.parquet``` ko pick kar leta hai.

<br>

**Main Conclusion**:

- Purane tarike mein: Athena ko pehle folder dhoodhna padta tha, aur fir folder ke andar ki saari files ko brute-force tarike se scan karna padta tha.
- Iceberg ke tarike mein: Athena index file se pehle hi pooch leta hai ki "kaun si exact file padhni hai?" aur S3 se sirf wahi ek file mangwata hai.

Isliye Iceberg use karne par query seconds mein khatam ho jaati hai aur scan size chota hone ki wajah se AWS ka kharcha 90% tak kam ho jata hai.

<br>

### Vector Bucket

Ye specifically AI aur Generative AI workloads ke liye introduce kiya gaya hai.

Generative AI aur LLMs (Large Language Models) mein data ko normal text ki jagah numbers ke array (jise Vectors ya Embeddings kehte hain) mein badla jata hai. Vector buckets in embeddings ko indexing ke sath store karte hain taaki AI search ya RAG (Retrieval-Augmented Generation) pipelines fast kaam kar sakein.

Iska purpose traditional files ya tabular data store karna nahi hai. Iska purpose vector data ko store aur query karna hai.

Iska sabse bada fayda yeh hai ki yeh Pinecone ya Weaviate jaise alag se chalne wale mehenge Vector Databases ke kharch ko 90% tak kam kar deta hai aur S3 ke andar hi Similarity Search (shabdon ke matlab ke hisab se dhoodhna) ki suvidha deta hai. Yeh duniya ka pehla aisa cloud object storage hai.

<br>

**Vector Embedding Kya Hoti Hai?**

Computer hamari tarah English ya Hindi nahi samajhta, aur AI models toh bilkul nahi samajhte.

AI ko jab koi data (jaise text, image, ya audio) samajhna hota hai, toh woh use lakho numbers ki ek list mein badal deta hai. Is numbers ki list ko technical bhasha mein "Vector" ya "Embedding" kehte hain.

Example: Agar AI ke samne ek shabd hai "King" (Raja), toh AI use backend par aise store karega: ```[0.23, -0.45, 0.89, 0.12...]```. Agar shabd hai "Queen" (Rani), toh uska vector hoga: ```[0.24, -0.44, 0.85, 0.11...]```.

Kyunki King aur Queen ka matlab aapas mein milti-julta hai, isliye unke yeh numbers (vectors) bhi aapas mein bohot paas-paas hote hain. AI isi numbers ki doori aur nazdiki se shabdon ka matlab samajhta hai.

AI models text, image ya other content ko numerical representation mein convert karte hain.

Example:
```
"Cloud Computing"

↓

[0.23, -0.67, 1.12, ...]
```

Ye vector embedding hoti hai.

AI application mein thousands, millions ya billions of embeddings ho sakti hain. Ab problem ye hai ki in vectors ko efficiently store aur search karna hota hai. Isi workload ke liye AWS ne S3 Vectors aur Vector Buckets banayi.

<br>

**Yeh Kyun Banaya Gaya?**

- **Pehele Kya Dikkat Thi**: Vector embeddings ko search karne ke liye aapko alag se mehnge aur hamesha chalne wale standalone Vector Databases (jaise Pinecone, Milvus ya OpenSearch) khareedne padte the.
- **S3 Vector Bucket ka Solution**: AWS ne is naye bucket type se alag database ka jhanjhat khatam kar diya. Aap direct S3 mein vectors daal sakte hain aur yeh dusre databases ke mukable 90% tak sasta (cost-optimized) padta hai.

<br>

**Real-World Example: AI Chatbot (RAG System)**:

Maan lijiye aapki company ka ek internal AI Chatbot hai jo employees ke sawalon ke jawab deta hai.

```
[User Query: "How to reset password?"] 
               |
               v (Turned into Vector)
      [ S3 Vector Bucket ] ---> (Looks into Vector Index)
               |
               v (Finds matching text snippet in milliseconds)
       [ AI Chatbot / LLM ] ---> [Perfect Answer Delivered]
```

- **Upload**: Aapne company ke saare internal documents ko vectors mein badla aur Amazon S3 Vector Bucket ke index mein save kar diya.
- **User Query**: Kisi employee ne poocha: "Account block ho gaya, kya karein?"
- **Similarity Search**: Chatbot is line ka vector banayega aur Vector Bucket se poochega ki iske jaisa milti-julti baat kis file mein likhi hai.
- **Fast Action**: S3 bina kisi lag ke, sub-second latency (kuch milliseconds) mein exact wahi documents dhoodh nikalega jahan password reset ya account recovery ki baat ho rahi hogi.
