# Bucket Policies (Bucket Level Security)

Pichhle concept mein humne IAM Policy dekhi thi, jisme hum IAM User, Group, ya Role ko permissions dete hain. Ab Bucket Policy mein approach ulta ho jata hai:
- IAM Policy mein hum identity se start karte hain aur decide karte hain ki ye identity kya access kar sakti hai.

Jabki:
- Bucket Policy mein hum bucket se start karte hain aur decide karte hain ki is bucket ya iske objects ko kaun, kis tarah, aur kin conditions ke under access kar sakta hai.

Bucket policy seedhe S3 Bucket (Resource) par lagayi jaati hai. Yeh bucket ko batati hai ki "Is bucket ke andar kaun-kaun aa sakta hai aur kya kar sakta hai." Kyunki yeh resource par lagti hai, isliye yeh kisi bhi bahar ke account ya anjaan user (anonymous user) par bhi control rakh sakti hai.

<br>

- **IAM Policies (User Level Security)**: Agar aapki company mein 10 employees hain, toh aap IAM (Identity and Access Management) policy se set kar sakte hain ki Puneet file upload kar sakta hai, par Rahul sirf file dekh sakta hai, delete nahi kar sakta.
- **Bucket Policies (Bucket Level Security)**: Yeh ek JSON script hoti hai jo seedhe bucket par lagayi jaati hai. Isse aap poore rule set kar sakte hain, jaise: "Sirf meri company ke IP Address se hi is bucket ka data open hona chahiye, baaki duniya ke liye block ho."

<br>

S3 Bucket Policy ek resource-based policy hoti hai jo directly S3 bucket ke saath attach ki jaati hai aur ye define karti hai ki kaun principal yaani User, Group, Role ya etc us bucket ya uske andar stored objects par kaunsa action perform kar sakta hai, kin conditions ke under kar sakta hai, aur kin resources par ye permission apply hogi.

Yeh ek JSON script hoti hai jo seedhe bucket par lagayi jaati hai. Matlab Bucket Policy ko bss S3 bucket ke ander jaake create karte hain aur wahi apply karte hain. Iska IAM console se koi lena dena nahi hota hai.

Bucket Policy ek resource-based policy hoti hai, json mein likhi jati hai, jo directly S3 bucket ke saath attach hoti hai.

Conceptually architecture aisa hai:
```
IAM User / IAM Role / AWS Account
             │
             │ Request
             ▼
      S3 Bucket
             │
             ▼
      Bucket Policy
             │
             ▼
      Allow / Deny decision
```
Jab koi principal S3 bucket ya uske objects ko access karne ki request karta hai, AWS applicable permissions aur policies evaluate karta hai.

**Example**:

Suppose tumhare paas ek bucket hai:
```
company-data
```
Is bucket ke andar objects hain:
```
company-data/
    │
    ├── images/
    │     ├── image1.jpg
    │     └── image2.jpg
    │
    ├── documents/
    │     └── report.pdf
    │
    └── backups/
          └── database-backup.sql
```

Ab tum bucket level par define karna chahte ho:
- Kaun is bucket ko access kar sakta hai?
- Kaun objects upload kar sakta hai?
- Kaun objects download kar sakta hai?
- Kaun objects delete kar sakta hai?
- Kaun sirf objects dekh sakta hai?
- Kaun kisi specific AWS account se access kar sakta hai?
- Kya public users access kar sakte hain?
- Kya access sirf ek particular VPC Endpoint ke through hona chahiye?
- Kya insecure HTTP requests ko block karna hai?

In sab rules ko define karne ke liye **Bucket Policy** use ki ja sakti hai. Aur ye bucket ke ander jake create hoti hai aur wahi apply hoti hai. Isme IAM ke though kuch nhi hota.

<br>

### Sabse pehle IAM Policy aur Bucket Policy ka difference samjho

Maan lo tumhare paas ek S3 bucket hai:
```
company-production-data
```
Aur tumhare paas ek IAM User hai:
```
Puneet
```

<br>

**IAM Policy ka perspective**

Agar tum Puneet ke IAM User par policy attach karte ho:
```
Puneet

↓

IAM Policy

↓

Allow s3:GetObject

↓

company-production-data/*
```

To policy essentially AWS ko bol rahi hai:
- Puneet ko is bucket ke objects read karne ki permission hai.

Yahan focus **Puneet identity** par hai.

<br>

**Bucket Policy ka perspective**:

Ab maan lo tum bucket par policy attach karte ho:
```
company-production-data

↓

Bucket Policy

↓

Puneet ko GetObject allow
```
Yahan focus identity par nahi, balki resource, yani bucket, par hai.

Bucket Policy essentially bol rahi hai:
- Is bucket par Puneet ko ye particular action perform karne ki permission hai.

Isliye:
```
IAM Policy = Identity-based Policy
```
Aur:
```
S3 Bucket Policy = Resource-based Policy
```

<br>
<br>

### IAM Policy aur Bucket Policy ka sabse bada conceptual difference

Maan lo tumhare paas ek employee hai: **Amit**.

Agar tum **IAM Policy** mein likhte ho:
- Amit, tum ```my-company-bucket``` ke objects read kar sakte ho.

To tum identity ko permission de rahe ho.
```
Amit
 │
 ▼
IAM Policy
 │
 ▼
S3 Bucket
```

Lekin **Bucket Policy** mein tum bucket ko instruction de rahe ho:
- ```my-company-bucket```, tum Amit ko apne objects read karne do.

```
Amit
 │
 ▼
S3 Bucket
 │
 └── Bucket Policy:
     Amit is allowed
```

Dono ka final result access allow karna ho sakta hai, lekin policy kis jagah attach hai aur permission kis perspective se define ki ja rahi hai, ye different hai.

### Jab access control karne ke liye IAM Policy thi, to Bucket Policy ko jarurat kyu padi?

Sabse bada reason hai ki kabhi-kabhi bucket owner ko resource ke level par control chahiye hota hai.

Maan lo tumhare paas ek production bucket hai:
```
company-production-data
```
Tum chahte ho:
- Sirf company account ke users access karein.
- Ek doosre AWS account ka role bhi access kar sake.
- Sirf HTTPS requests allow hon.
- Public access completely block ho.
- Specific IP range se access allow ho.
- Kuch specific objects public read hon.

Aise rules bucket ke perspective se define karna Bucket Policy mein bahut useful hota hai.

Aur iska seedha jawab hai: IAM Policy "Account" ke andar ke logon ko milti hai, lekin Bucket Policy "S3 Bucket" par lagai jati hai. Bucket Policy "S3 Bucket" ke darwaze par pehra deti hai.

Kuch aise use-cases (scenarios) hain jo IAM Policy akele kabhi poore nahi kar sakti thi. Isi wajah se Bucket Policy ki zaroorat padi:

**1. Cross-Account Access (Dusre Account Ke Logon Ko Access Dena)**:

Maan lijiye aapka ek dost hai jiska apna ek alag AWS account hai (Account B), aur aapka account hai (Account A). Aap chahte hain ki aapka dost aapki bucket (```meri-bucket-puneet```) se data download kar sake.

- **IAM Policy Kyu Fail Hui?** Aap ```Account A``` ke IAM console mein baith kar ```Account B``` ke kisi user ke liye policy nahi bana sakte. IAM sirf aapke khud ke account ke employees/users ko control karta hai. IAM policy hamesha apne hi account ke users par lagti hai.
- **Bucket Policy Kyu Jeet Gayi?** Aap apni bucket par ek Bucket Policy lagate hain aur usme likhte hain: "Allow Account B's user to get objects". Kyunki policy bucket par lagi hai, yeh bahar ke account ke logon ko bhi andar aane ki permission de sakti hai.

IAM Policy tab tak fail hai jab tak saamne wala user aapke same AWS account ka hissa na ho. Cross-Account sharing ke liye Bucket Policy compulsory ho jaati hai.

<br>

**2. Public Anonymous Access (Duniya Ke Liye Files Open Karna)**:

Maan lijiye aap S3 par ek Static Website host kar rahe hain, ya fir aapki mobile app ki images S3 mein hain jo poori duniya ke liye public karni hain:

- **IAM Policy Kyu Fail Hui?** Internet par website dekhne wale log aapke AWS account ke users nahi hain. Aap duniya ke har ek insaan ke liye IAM user nahi bana sakte. IAM policy kisi anjaan (anonymous) internet user par nahi lagayi jaati.
- **Bucket Policy Kyu Jeet Gayi?** Bucket policy mein ek option hota hai Principal: "```*```". Iska matlab hai "Duniya ka koi bhi anjaan insaan (Anonymous User)". Isse aap ek click mein poori bucket ke objects ko pure internet ke liye public read-only bana sakte hain. Isse internet par maujood koi bhi vyakti bina kisi AWS login ke aapke S3 assets ko dekh sakta hai.

<br>

**3. Strict Centralized Control**:

Maan lijiye aapki company mein 500 developers hain aur sabke paas alag-alag IAM permissions hain (kisi ke paas zyada, kisi ke paas kam). Aapko dar hai ki koi developer galti se koi mehenga ya sensitive data delete na kar de.

- **IAM Policy Kyu Fail Hui?** Aapko sabhi 500 developers ki IAM policies ko ek-ek karke check karna padega ki kahin kisi ko galti se delete ki permission toh nahi mili. Yeh manage karna namumkin hai.
- **Bucket Policy Kyu Jeet Gayi?** Aap bucket par ek single policy laga dete hain: "Deny Everyone from deleting files". Kyunki AWS ka niyam hai ki Deny humesha Allow se bada hota hai, ab chahe kisi developer ke paas IAM mein full access bhi ho, bucket policy use file delete karne se rok degi. Safe and Secure!

<br>

**4. Network/IP-Based Restrictions (Office Ke Bahar Access Block)**:

Aapki company ka niyam hai ki S3 ka data sirf office ke andar ke computers par hi khulna chahiye. Agar koi employee ghar se baith kar data download kare, toh block ho jana chahiye.

- **IAM Policy Kyu Fail Hui?** IAM ka focus user par hota hai, network conditions par nahi.
- **Bucket Policy Kyu Jeet Gayi?** Bucket policy mein aap condition laga sakte hain ```aws:SourceIp```. Isme aap apne office ka WiFi/Network IP address daal dete hain. Ab agar koi sahi password lekar ghar se bhi login karega, toh bucket policy use data access nahi karne degi.

<br>

**Conclusion**:

AWS mein S3 Bucket Policy ki zaroorat isliye padi taaki:
- Bahar ke accounts (Cross-account) ko access diya ja sake.
- Poori duniya ke liye Public Access open kiya ja sake.
- Bucket ke upar ek Centralized Security Layer lagayi ja sake jo IAM users ki galtiyon ko rok sake.

### Bucket Policy ko "Bucket-Level Security" kyun kehte hain?

IAM identity-based policy kisi identity ke saath attach hoti hai, jaise:
- IAM User
- IAM Group indirectly through attached policy
- IAM Role

Lekin Bucket Policy directly **S3 resource**, yani bucket, ke saath attach hoti hai.

Architecture:
```
IAM User
    │
    └── Identity-Based Policy


IAM Role
    │
    └── Identity-Based Policy


S3 Bucket
    │
    └── Bucket Policy
```

Isliye Bucket Policy ko resource-based policy kaha jata hai.

Yahan policy ye keh sakti hai:
- "Mera S3 bucket kis-kis ko access allow karega aur kis type ka access allow karega."

Yani IAM policy ka focus aksar hota hai:
```
Identity → Resource
```
Jabki Bucket Policy mein perspective hota hai:
```
Resource → Kaun access kar sakta hai?
```

### Bucket Policy ka basic structure

Ek Bucket Policy JSON format mein likhi jaati hai.

Basic structure kuch is tarah hota hai:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```

Ab is policy ke har component ko detail mein samajhte hain.

**Version**:

Example:
```
"Version": "2012-10-17"
```

Yahan ```Version``` S3 bucket ki versioning se related nahi hai. Ye bucket policy language ka version identifier hai.

Commonly:
```
2012-10-17
```
use kiya jata hai. Yani ye policy syntax aur policy language ka version define karta hai.

<br>

**Statement**:

Policy ke andar actual permission rules ```Statement``` ke andar likhe jaate hain. Statement ke andar actual permission rules hote hain.

Example:
```
"Statement": [
    {
        ...
    }
]
```

Ek policy mein ek se zyada statements ho sakte hain.

Example:
```
Statement 1
↓
Allow specific role to read objects

Statement 2
↓
Allow application to upload objects

Statement 3
↓
Deny access if request is not using HTTPS
```

Yani ek hi Bucket Policy ke andar multiple security rules define kiye ja sakte hain.

<br>

**Effects**:

```Effect``` AWS ko batata hai ki rule kya kar raha hai, Allow ya Deny. Matlab Bucket Policy mein kya operations allowed hain ya nhi.

Matlab policy ke ander jab rule ko apply karna ho to Effect ko ```Allow``` karte hain, Lekin jab rule ko hatana ho to ```Deny``` karte hain.

Do primary values hoti hain:
```
Allow
```
aur
```
Deny
```

Example:
```
"Effect": "Allow"
```
Iska matlab hai ki policy specified principal ko specified action perform karne ki permission de rahi hai.

Example:
```
"Effect": "Deny"
```
Iska matlab hai ki policy specified request ko explicitly reject kar rahi hai.

<br>

**Explicit Deny bahut important concept hai**:

AWS permissione evaluation mein **Explicit Deny** ki priority Allow se zyada hoti hai.

Suppose ek IAM User ke paas IAM Policy ke through permission hai:
```
Allow → s3:GetObject
```

Lekin Bucket Policy mein likha hai:
```
Deny → s3:GetObject
```

Aur dono policies us particular request par apply ho rahi hain.

To final result hoga:
```
Explicit Deny
```

Yani access reject ho jayega.

Flow:
```
IAM Policy
    │
    └── Allow GetObject

Bucket Policy
    │
    └── Explicit Deny GetObject

Final Result
    │
    ▼
Access Denied
```
AWS permission evaluation mein Explicit Deny bahut powerful rule hai.

<br>

**Principal**:

Principal batata hai:
- Kisko ye permission di ja rahi hai ya kiske liye ye rule apply ho raha hai?

Example:
```
"Principal": {
  "AWS": "arn:aws:iam::123456789012:user/Puneet"
}
```
Iska matlab hai ki rule specifically Puneet naam ke IAM User ke liye define kiya gaya hai.

Principal ho sakta hai:
- Specific IAM User.
- Specific IAM Role.
- AWS Account.
- AWS Service.
- Public users.

Principal ke different examples:

Specific IAM User:
```
arn:aws:iam::123456789012:user/Puneet
```

Specific IAM Role:
```
arn:aws:iam::123456789012:role/ApplicationRole
```

Entire AWS Account
```
arn:aws:iam::123456789012:root
```
Yahan root ka matlab ye nahi hai ki sirf root user ko permission mil rahi hai. Resource-policy principal syntax mein ye generally us AWS account ko represent kar sakta hai, aur exact effective access IAM evaluation par depend karta hai.

Everyone:
```
"Principal": "*"
```
Iska matlab generally hai: ```Any Principal```.

Iska matlab broadly anonymous ya any principal ke liye policy rule apply karne ki intention ho sakti hai.

Lekin production environment mein ```Principal: "*"``` bahut carefully use karna chahiye. Kyunki galat configuration se bucket ya objects public ho sakte hain.

```Principal: "*"``` ka matlab automatically ye nahi hota ki bucket bina kisi restriction ke public accessible ho hi jayega.

Actual result doosri conditions aur security controls par bhi depend karega, jaise:
- Bucket Policy ke remaining rules.
- S3 Block Public Access settings.
- Object ownership configuration.
- Applicable IAM permissions.
- Explicit Deny.

Isliye ```Principal: "*"``` ko production mein bina samjhe use nahi karna chahiye.

<br>

**IAM Policy mein Principal usually kyun nahi hota, lekin Bucket Policy mein hota hai?**

IAM identity policy already kisi identity par attached hoti hai.

Example:
```
IAM User Puneet

↓

IAM Policy
```

AWS ko already pata hai:
- Ye policy Puneet ke liye hai.

Isliye identity-based policy mein generally separate Principal specify nahi karna padta.

Lekin Bucket Policy bucket par attached hoti hai. Bucket khud koi user nahi hai. Isliye bucket ko explicitly batana padta hai:
- Ye permission kis identity ko deni hai?

Isliye Bucket Policy mein Principal important hota hai.

<br>

**Action**:

```Action``` batata hai ki principal S3 par kya operation perform kar sakta hai. Matlab hum konsa rule hai jo allow ya deny kar rahe hain, Action vo particular rule hota hai.

Example:
```
"Action": "s3:GetObject"
```
Iska matlab object read/download.

Kuch common actions hain:
- Objects read karne ke liye: ```s3:GetObject```.
- Objects upload karne ke liye: ```s3:PutObject```.
- Objects delete karne ke liye: ```s3:DeleteObject```.
- Bucket ke objects list karne ke liye: ```s3:ListBucket```.

Ya multiple actions:
```
"Action": [
    "s3:GetObject",
    "s3:PutObject"
]
```

<br>

**Resource**

Resource batata hai ki rule kis S3 resource par apply hoga. Jo rule humne allow ya deny kiya hai vo AWS ki konsi S3 bucket par apply hoga.

S3 mein Resource ARN ke through specify kiya jata hai. ARN ek string hoti hai jo AWS resource ko AWS par uniquely identify karne ke liye hoti hai.

Suppose bucket ka naam hai: ```company-data```.

Suppose tum action use karte ho, matlab rule apply karte ho:
```
s3:ListBucket
```
Ye ek bucket par apply hone wala action ya rule hai.

Isliye tumko ```resource``` mein bucket ARN dena hoga:
```
arn:aws:s3:::company-data
```

Lekin agar tum bucket ke objects par action ya rule apply karna chate ho, Jaise:
```
s3:GetObject
```
Ye object par apply hone wala rule hai.

To tumko ```resource``` mein object ARN dena hoga.
```
arn:aws:s3:::company-data/*
```
Yahank ye ```/*``` bucket ke ander sabhi objects ko represent karta hai.


Example:

Suppose bucket: ```company-data```.

User objects ki list dekhna chahta hai, Uske liye:
```
s3:ListBucket
```

Aur resource:
```
arn:aws:s3:::company-data
```
chahiye.

Lekin user file download karna chahta hai:
```
company-data/report.pdf
```
To action:
```
s3:GetObject
```

Aur resource:
```
arn:aws:s3:::company-data/*
```
hoga.

Isliye ek complete read policy aksar dono permissions include karti hai:
```
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/Amit"
      },
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-data"
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/Amit"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-data/*"
    }
  ]
}
```

### Bucket Policy mein Condition kya hota hai?

**Condition** ka use karke hum permission ke saath extra requirements attach kar sakte hain.

Matlab:
- Principal ko permission tabhi milegi jab specified condition satisfy hogi.

Example conditions:
- Request HTTPS ke through aaye.
- Request specific IP address se aaye.
- Request specific VPC Endpoint se aaye.
- Request particular AWS Account se aaye.
- Request particular encryption requirements follow kare.

<br>

**Condition Block Ka Structure**:

Ek Bucket Policy mein Condition is tarah likhi jaati hai:
```
"Condition": {
    "Condition-Type": {
        "Condition-Key": "Value"
    }
}
```
Exaplanation:
- **Condition-Type**: Aap kis tarah ki cheez check kar rahe hain? Jaise: String, Number, IP Address, ya Date.
- **Condition-Key**: AWS ka woh predefined variable jise aap check karna chahte hain (jaise: ```aws:SourceIp``` ya ```s3:x-amz-server-side-encryption```).
- **Value**: Woh exact value jisse aap match karna chahte hain.

<br>

**Sabse Zyada Use Hone Wali 5 Mahatvapurna Conditions**:

**A. IP Address Restriction (Office Network Block)**:

Aap chahte hain ki aapka sensitive data sirf aapke office ke network se hi access ho. Agar koi employee ghar se ya public Wi-Fi se access kare, toh block ho jaye.
- Condition Type: ```NotIpAddress``` (Agar yeh IP nahi hai toh).
- Key: ```aws:SourceIp```.

Example:
```
"Condition": {
    "NotIpAddress": {
        "aws:SourceIp": "203.0.113.0/24" 
    }
}
```
Kaise kaam karta hai: Agar aane wali request ka IP address 203.0.113.0/24 nahi hai, toh yeh condition match ho jayegi, aur agar iske sath Deny laga hai, toh user block ho jayega.

<br>

**B. Enforce HTTPS (Secure Transport Only)**:

Aap chahte hain ki data aate-jaate waqt internet par hamesha encrypted rahe (```https://```). Agar koi bina security ke (```http://```) request kare, toh use mna kar diya jaye.
- Condition Type: ```Bool``` (True ya False).
- Key: ```aws:SecureTransport```.

Example:
```
"Condition": {
    "Bool": {
        "aws:SecureTransport": "false"
    }
}
```
Kaise kaam karta hai: Agar ```SecureTransport``` (HTTPS) ki value ```false``` hai (yaani s3 ke pass aane wali request unsecured hai), toh yeh shart poori ho jayegi aur request ko turant ```Deny``` kar diya jayega.

<br>

**C. Enforce Server-Side Encryption (Data-at-Rest Security)**:

Aap chahte hain ki is bucket mein koi bhi file bina encryption ke upload na ho sake. Agar koi user bina encryption header ke file bhejta hai, toh bucket use accept hi nahi karega.
- Condition Type: ```StringNotEquals```.
- Key: ```s3:x-amz-server-side-encryption```.

Example:
```
"Condition": {
    "StringNotEquals": {
        "s3:x-amz-server-side-encryption": "AES256"
    }
}
```
Kaise kaam karta hai: Agar upload request mein encryption ka tarika AES256 nahi hai, toh bucket upload ko reject kar dega. Isse company ka compliance barkarar rehta hai.D. Multi-Factor Authentication (MFA) Enforcement

<br>

**D. Multi-Factor Authentication (MFA) Enforcement**:

User S3 par uploaded kuch file ko delete karna chta hai. Bohot sensitive data (jaise financial records) ke liye aap chahte hain ki user ke paas sirf username/password hona kaafi nahi hai. Usne apne phone par MFA (OTP) code dala ho, tabhi data delete karne mile.
- Condition Type: ```Bool```.
- Key: ```aws:MultiFactorAuthPresent```.

Example:
```
"Condition": {
    "Bool": {
        "aws:MultiFactorAuthPresent": "false"
    }
}
```
Kaise kaam karta hai: Agar user bina MFA login ke aaya hai (```MFA Present = false```), aur woh koi file delete (```s3:DeleteObject```) karne ki koshish karta hai, toh use block kar diya jayega.

<br>

**E. Strict VPC Endpoint Restriction (Private Cloud Only)**:

Aap chahte hain ki S3 bucket internet par bilkul na dikhe. Sirf aapke AWS ke andar jo VPC (Virtual Private Cloud) ya EC2 instances chal rahe hain, unhi ke andar se data access ho sake.
- Condition Type: ```StringNotEquals```.
- Key: ```aws:sourceVpce (VPC Endpoint ID)```.

Example:
```
"Condition": {
    "StringNotEquals": {
        "aws:sourceVpce": "vpce-1a2b3c4d"
    }
}
```
Kaise kaam karta hai: Agar request is specific private endpoint se nahi aa rahi hai, toh use poori tarah block kar diya jata hai, chahe woh user account ka admin hi kyu na ho.

<br>
<br>

**Ek Real AWS Policy Code Example**:

Chaliye ek real JSON bucket policy dekhte hain jo do sharto ko ek sath jodti hai:
- Yeh poori duniya (```*```) ke liye hai.
- Lekin yeh sirf tabhi Allow karegi jab request HTTPS se aayegi AUR aapke Office IP se aayegi.

```
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "RestrictToOfficeAndHTTPS",
            "Effect": "Allow",
            "Principal": "*",
            "Action": [
                "s3:GetObject",
                "s3:PutObject"
            ],
            "Resource": "arn:aws:s3:::mera-secure-bucket/*",
            "Condition": {
                "IpAddress": {
                    "aws:SourceIp": "192.0.2.0/24"
                },
                "Bool": {
                    "aws:SecureTransport": "true"
                }
            }
        }
    ]
}
```

Pro-Tip: Multi-Value Conditions Kaise Kaam Karti Hain?
- Agar aap ek hi Condition ke andar multiple keys likhte hain (jaise upar ke example mein ```IpAddress``` aur ```Bool``` dono hain), toh AWS unke bich mein **AND** logic lagata hai. Yaani dono shartein poori hona zaroori hain.
- Agar aap ek hi key ke andar multiple values likhte hain, jaise ["```192.0.2.0/24```", "```198.51.100.0/24```"], toh AWS unke bich mein **OR** logic lagata hai. Yaani dono mein se koi bhi ek IP hoga toh chalega.
